# 用 50 万参数的 Transformer 写 Python 代码

一个完整可跑的小项目：**按论文《Attention Is All You Need》的架构实现 Transformer，
参数精确控制在 50 万，训练它生成 Python 代码，并给它找一个参照系。**

论文原版是 6500 万参数、8 块 P100 训练 12 小时。这里等比缩小约 130 倍，
在笔记本的 RTX 5060（8 GB 显存）上 **约 3.4 分钟**训练完。

---

## 结果速览

在**没有参与训练**的独立测试集（标准库 `Lib/test` 的 40 个文件，40 万字符）上：

| 指标 | 数值 | 说明 |
|---|---|---|
| 困惑度 ppl | **4.460** | 字符级；旧语料（630 万）是 5.264 |
| n-gram 基线 ppl | 5.631 | 只数数、不学习的 5-gram，同一测试集 |
| 签名合法率 | 31.7% | 生成 60 个样本，首行是合法 `def f(x):` 的比例 |
| 注意力熵（层 1 / 层 2） | 0.59 / 1.90 | 浅层看局部、深层看全局 |

三条结论：

1. **参数量决定「能不能写出函数签名」，语料决定「签名写得好不好」**——从 10 万加到 50 万，
   签名合法率 11.7% → 31.7%；换 3.3 倍语料，这个数一个点都没动。
2. **ppl 和生成质量不是同一条线**——扩语料让 ppl 降 15.3%，但 `class` 的格式正确率从 17% 掉到 0%。
   追查发现旧模型那 17% 靠的是背语料，扩语料只是揭穿了它原本就没学会。
3. **同容量下 Transformer 比 n-gram 好 26%**（4-gram 表 50.1 万格 vs 49.5 万参数），
   差距来自参数共享，不是上下文长度——给 n-gram 无限上下文也只追到 5.530。

完整实验记录见 [`docs/技术报告.md`](docs/技术报告.md)（8 节，5 组实验，全部数字可复现）。

## 快速开始

```powershell
# 1. 准备语料（从本机 Python 标准库 + site-packages 提取，不需要联网）
python src/prepare_data_big.py

# 2. 训练（约 3.4 分钟，30,000 步）
python src/train.py --corpus data/corpus_big.txt --vocab data/vocab_big.json `
    --ckpt results/model_big.pt --log results/train_log_big.csv `
    --steps 30000 --eval-batches 100

# 3. 生成代码
python src/generate.py --ckpt results/model_big.pt --prompt "def " `
    --tokens 300 --temperature 0.6 --top-k 10

# 4. 看注意力头学到了什么
python src/visualize_attention.py --ckpt results/model_big.pt
```

想要最快跑通？直接 `python src/train.py`（默认配置，630 万字符语料，12,000 步，约 82 秒）。

## 模型与论文的对应关系

代码里每个类都标了论文的章节号，方便对照译文阅读：

| 论文位置 | 内容 | 代码 |
|---|---|---|
| §3.2.1 式(1) | `Attention(Q,K,V) = softmax(QK^T/√d_k)V` | `ScaledDotProductAttention` |
| §3.2.2 | 多头注意力 `Concat(head_1..head_h)W^O` | `MultiHeadAttention` |
| §3.3 式(2) | `FFN(x) = max(0, xW_1+b_1)W_2+b_2` | `PositionwiseFeedForward` |
| §3.1 | 残差连接 + 层归一化 | `DecoderLayer` |
| §3.2.3 | 因果掩蔽（阻止看到未来位置） | `forward` 中的 `torch.tril` 掩码 |
| §3.4 | 嵌入与输出层权重共享、乘 `√d_model` | `TinyTransformer` 的 `tie_weights` 与 `scale` |
| §3.5 | 正弦位置编码 | `PositionalEncoding` |
| §5.3 式(3) | 学习率预热与衰减 | `train.py` 的 `lr_lambda_factory` |
| §5.4 | 残差 dropout `P_drop=0.1` | 各处 `nn.Dropout` |

### 与论文的差异（有意为之）

- **只实现了解码器。** 论文用于翻译，是编码器-解码器结构；本任务是自回归语言建模，
  只需解码器。解码器内部结构（掩蔽自注意力 + 残差 + 层归一化 + 前馈）与论文完全一致。
- **未实现编码器-解码器交叉注意力**，因为该任务没有独立的编码器输入。
- **层数减为 2**（论文 6），`d_model` 减为 128（论文 512），以适配 50 万参数与单卡笔记本。

## 参数量构成

```
d_model=128   n_heads=8   d_k=16   d_ff=680   n_layers=2   vocab=96

词嵌入（与输出层权重共享）      12,288
第 1 个解码器层               241,448
  ├─ 多头注意力 4×(128×128+128)          66,048
  ├─ 前馈 (128×680+680)+(680×128+128)   174,888
  └─ 两个 LayerNorm                       512
第 2 个解码器层               241,448
输出层归一化                      256
----------------------------------------
合计                          495,440
```

论文 base 模型：`d_model=512, n_heads=8, d_ff=2048, n_layers=6, vocab≈37000`，共 6500 万。

**为什么 `d_ff=680` 这么奇怪的数字？** 为了让总量落在 50 万附近。
取值来自参数扫描（10 万 / 30 万 / 50 万 / 94 万四档）：

| 参数量 | val_loss | ppl | 训练耗时 | 备注 |
|---|---|---|---|---|
| 100,048 | 1.9039 | 6.71 | 78 s | 写得出 `def`，写不出参数名 |
| 302,096 | 1.7683 | 5.86 | 80 s | |
| 495,440 | 1.7270 | 5.62 | 77 s | ← 630 万语料下的最优点 |
| 937,216 | 1.7048 | 5.50 | 133 s | 好 1.3%，但 9,000 步后过拟合 |

语料扩到 2,097 万后，这个排序反过来了：94 万（val 1.3358）比 50 万（1.4293）好 **6.54%**。
**「多少参数最好」不是模型的固有属性，是模型与数据量的联合结果。**

## 语料说明

两套语料，都在本机生成，零网络依赖：

| | 来源 | 规模 | 词表覆盖 |
|---|---|---|---|
| 旧 | Python 标准库 | 630 万字符 | 99.996% |
| 新 | 标准库 + site-packages（torch / numpy / pandas …） | 2,097 万字符 | 99.9997% |

选择理由：**规模合适**（足够让 50 万参数学到语法结构）、**结果可判断**（写出的东西像不像
Python 代码，肉眼一看便知）、**可做无污染测试**（数据准备脚本的目录黑名单里排除了 `test`，
标准库 `Lib/test` 正好当测试集）。

扩语料时踩过一个坑，值得记：**非 ASCII 字符会把词表挤爆**。
标准库源码 98.8% 是 ASCII，剩下 1.2% 是 docstring 里的 emoji、重音字母，
字符种类高达 4,682 种——而词表只有 96 个位置。结果 `^` 和 `&` 这类真正的运算符落榜，
模型永远写不出 `a & b`。

修法是只保留纯 ASCII 行：代价是丢 1.2% 字符，收益是字符种类 4,682 → 96、零 OOV。

## 两个值得记录的 bug

### 1. 学习率小了 1000 倍

第一版训练时 loss 从 4.57 降到 3.71 就几乎不动了，生成的文本是乱码：

```
def  ,
dcul" ac #nok)n
 ll.,ol)n.=s da&t pp)
```

**症状像是模型容量不足，但真正的原因是学习率。**

论文式(3) 在步数 3000 时应为 `2.28e-03`，而实际只用了 `2.28e-06`：

```python
opt = torch.optim.Adam(model.parameters(), lr=1e-3)     # ← 问题在这
sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_lambda)
```

`LambdaLR` 的实际学习率是 **`optimizer` 的 `base_lr` × `lambda(step)`**。
我误以为 lambda 的返回值就是最终学习率，于是它被 `1e-3` 又缩小了 1000 倍。

修正方式是让 lambda 直接返回论文公式的值，并把 `base_lr` 设为 1.0：

```python
opt = torch.optim.Adam(model.parameters(), lr=1.0)      # ← 修正
```

**教训**：loss 不降有很多种原因，不要一上来就怀疑模型太小或数据太少。
先把论文里的关键数值**算出来，和实际用的对一遍**——这次一算就发现差了三个数量级。

### 2. 词表换了，模型静默输出乱码

扩语料后重新生成了 `vocab_big.json`。新旧词表都是 96 个字符，但 **id 只有 20 个对得上**——
同一个 id 在旧表里是 `d`，在新表里可能是 `q`。加载旧权重要是配上新词表，
不会报任何错，只会吐出乱码。

修法：checkpoint 里存 `vocab_file` 路径，生成/评测脚本从 checkpoint 读词表，
不再让调用方自己传。**这类「不报错但结果全错」的 bug 最贵**，得靠结构防，不能靠人细心。

## 可以自己试的实验

这个项目的价值在于**可以改**。几个直接可做的：

1. **改 `n_heads`**：`n_heads=1` 会怎样？论文表 3 的 (A) 行做过这个消融，
   结论是单头比最佳设置差 0.9 BLEU。你能在小模型上重现类似现象吗？
2. **改 `d_k`**：论文 (B) 行发现减小 `d_k` 会损害质量，为什么？
3. **去掉位置编码**：模型还能学会顺序吗？（论文 §3.5 讨论过这个）
4. **换语料**：换成中文文本、或你自己的笔记，看生成结果怎么变
5. **调温度**：`temperature=0.3` 和 `1.5` 的输出差别说明了什么？
6. **改 n-gram 的阶数**：`--max-order 3` 和 `5` 的差距有多大？为什么旧语料上 5 阶反而更差？

跑第 1 或第 2 个实验时，把结果和论文表 3 对照——**这是从小模型实验理解大模型结论的练习**，
也是科研里常见的思维方式。
