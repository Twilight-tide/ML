# Transformer 语言模型：参数规模、内部机制与能力边界

**实验时间**：2026 年 11 月
**代码**：`src/`（模型、训练、生成、可视化）
**产物**：`results/model.pt`（495,440 参数）、`results/model_big.pt`、`results/train_log.csv`、
`results/attention_*.png`、`results/ngram_baseline.csv`（§6 基线）

---

## 摘要

本项目在一个按论文架构实现的解码器-only Transformer 上，做了五组实验：

1. **参数规模扫描**（10 万 → 94 万）：测出旧语料（630 万字符）下的最优参数规模是 50 万，94 万只比它好 1.3%，但训练慢 73% 且已出现明显过拟合。
2. **注意力层分工观察**：模型自发形成「第 1 层看局部、第 2 层看全局」的分工，用注意力熵定量验证（层 1 均值 0.61，层 2 均值 1.95）。换成 3.3 倍语料后该模式稳定复现（0.59 / 1.90）。
3. **能力边界的频率解释**：生成质量与语料中该模式的频次强相关——出现 9000 次以上的关键字（`if`/`def`/`return`）能写出语法正确的代码，出现 2000 次左右的（`class`/`import`）退化成自然语言散文。
4. **扩语料的效果与边界**：语料从 630 万扩到 2,097 万字符，在同一独立测试集上困惑度从 5.264 降到 4.460（−15.3%）。但 `class` 的格式正确率反而从 17% 掉到 0%——追查发现旧模型那 17% 来自记忆而非泛化，扩语料只是揭穿了它原本就没学会。
5. **n-gram 基线**：用一个只数数、不学习的字符级 n-gram 做同一道题，给 ppl 找刻度。参数量对齐时（4 阶表 501,300 格 vs 495,440 参数）Transformer 的 ppl 低 26.2%；把 n-gram 的计数表扩到 3.6 倍（178 万格），仍差 20.8%。

前四条指向同一件事：**瓶颈不在参数量，在数据；但加数据不是万能的，它会同时提升整体指标、暴露真实的局部缺陷。**
第五条给了它们一个参照系：**ppl 4.460 既不是天花板也不是地板，它比「只数数」好两成多，但离「真懂代码」还很远。**

## 1 项目概述

### 1.1 模型结构

按《Attention Is All You Need》实现，做自回归语言建模（只用解码器）：

| 项目 | 本模型 | 论文 base |
|---|---|---|
| 层数 N | 2 | 6 |
| d_model | 128 | 512 |
| 注意力头数 h | 8 | 8 |
| d_k = d_model/h | 16 | 64 |
| d_ff | 680 | 2048 |
| 参数量 | 495,440 | 65M |
| 分词粒度 | 字符级（词表 96） | BPE（37k） |

**保留的论文要素**：缩放点积注意力（式 1）、多头注意力（式 2）、正弦位置编码（式 3）、残差 + LayerNorm、权重共享、warmup 学习率（式 4）。

**省略的要素**：编码器与交叉注意力（任务是纯生成，无源序列）。

### 1.2 语料与训练

```
语料      两套：630 万字符（标准库，§2–§4）与 2,097 万字符（+site-packages，§5）

序列长度  64
批大小    32
学习率    Adam，β=(0.9, 0.98)，warmup 200 步后按步数平方根反比衰减
正则化    dropout 0.1 + 梯度裁剪 1.0
```

## 2 实验一：参数规模的影响

> **注意**：本节结论建立在 630 万字符的旧语料上，其中「50 万最优」一条
> 已被 §5.6 推翻——语料扩到 2,097 万后，94 万参数反而好 6.54%。本节保留原样作为记录。

### 2.1 方法

固定数据、随机种子（42）、批大小、序列长度、训练步数（12000），只改变模型尺寸。参数量通过调整 `d_model`、`n_heads`、`d_ff`、`n_layers` 控制。

四组配置：

| 组 | d_model | 头数 | d_ff | 层数 | 参数量 |
|---|---|---|---|---|---|
| A | 64 | 4 | 232 | 2 | 100,048 |
| B | 96 | 6 | 560 | 2 | 301,024 |
| D | 128 | 8 | 680 | 2 | 495,440 |
| C | 128 | 8 | 640 | 4 | 937,216 |

### 2.2 结果

| 配置 | 参数量 | 最优 val | ppl | 最优步数 | 训练耗时 |
|---|---|---|---|---|---|
| A | 100,048 | 1.9039 | 6.71 | 10,000 | 78 s |
| B | 301,024 | 1.7683 | 5.86 | 12,000 | 80 s |
| **D** | **495,440** | **1.7270** | **5.62** | **12,000** | **77 s** |
| C | 937,216 | 1.7048 | 5.50 | 9,000 | 133 s |

相对基准 A 的提升：B +7.1%，D +9.3%，C +10.5%。

### 2.3 分析

**（1）收益递减**

```
A → B：参数 ×3.0，val 降 7.1%
B → D：参数 ×1.6，val 降 2.3%
D → C：参数 ×1.9，val 降 1.3%
```

同样的参数增长速度，收益在持续衰减。

**（2）深度比宽度贵得多**

C 与 D 宽度相同（d_model=128），只差层数（4 vs 2）：

```
层数 2 → 4：训练时间 77s → 133s（+73%）
```

原因在计算结构：宽度增加让矩阵乘变大（GPU 并行，代价低）；层数增加是**串行**的，第 2 层必须等第 1 层完成。

**（3）94 万参数已经过拟合**

C 的验证损失在 9000 步达到最低（1.7048），之后回升：

```
step  9000   1.7048   ← 最低点
step 10000   1.7210
step 12000   1.7964   ← 比 B 的最优值还差
```

train/val 差距同步扩大：

| 配置 | train | val | 差距 |
|---|---|---|---|
| A | 1.6751 | 1.9138 | 0.24 |
| B | 1.4730 | 1.7683 | 0.30 |
| D | 1.4027 | 1.7270 | 0.32 |
| C | 1.3373 | 1.7964 | **0.46** |

C 的训练损失最低，验证损失最差——典型的记忆训练集。

### 2.4 结论

**50 万是当前语料下的最优点。**

选择依据不是「最大最好」，而是性价比：94 万比 50 万多花一倍参数、多等 73% 时间，只换来 1.3% 的提升，并且已经在背答案。

用经验法则验证：50 万参数配 630 万字符，比例 1:13；94 万的比例是 1:7，低于常用的 1:20。**数据量不足时，加大参数只会加速过拟合。**

## 3 实验二：注意力层的分工

### 3.1 方法

让模型处理一段有结构的代码（`def __init__(self, config):` + 缩进的赋值语句），取出每层每个头的注意力权重矩阵，计算每行分布的熵：

```
H = -Σ p_i · log(p_i)
```

熵越低表示注意力越集中（几乎只看一个位置），越高表示越分散。

### 3.2 结果

**各头的熵**（序列长度 53，取平均）：

```
层 1：0.92  0.58  0.55  0.68  1.06  0.41  0.12  0.53    均值 0.61
层 2：1.75  1.94  2.08  1.62  1.92  1.87  2.05  2.37    均值 1.95
```

**可视化**（`results/attention_layer_avg.png`）：

- 层 1 的权重集中在紧邻前一个位置，图上是一条锐利的对角线
- 层 2 没有对角线，亮点散布在整个左下三角区域

### 3.3 分析

**（1）分工是自发形成的**

论文没有规定「浅层做局部、深层做全局」。这个结构是训练中自己形成的：局部模式（相邻字符搭配）在第一层就能解决，第二层没必要重复，于是转向更远的关系。

**同样的分工在 GPT-2、BERT 等大模型上都被观察到。** 一个 50 万参数、用 630 万字符训练的小模型，复现了这个结构。

**（2）层 1 头 7 是「前一个 token 头」**

其熵只有 **0.12**，对应图上最锐利的那条对角线——它几乎只做一件事：看紧邻的前一个字符。

这类头在真实模型中被命名为 previous-token head，是语法处理的基础组件之一。

**（3）实现正确性得到验证**

```
每行权重和    ∈ [1.000000, 1.000000]   → softmax 归一化正确
未来位置权重  = 0.00e+00                → 因果掩蔽正确
```

第二条尤其关键：掩码写错时右上三角会出现非零值，模型等于在训练时抄答案。

## 4 实验三：能力边界与语料频率

### 4.1 方法

用相同的温度（0.3 / 0.7）、top-k=10、固定种子，对五个不同的起始关键字各生成 60 个字符，人工判断语法正确性。

同时统计各关键字在语料中的出现次数。

### 4.2 结果

| 提示词 | 语料频次 | 生成结果（T=0.3） | 语法 |
|---|---|---|---|
| `if ` | 16,937 | `if not self._set_path is None:` | ✓ 正确 |
| `def ` | 9,387 | `def __init__(self, args):` | ✓ 正确 |
| `return ` | 9,278 | `return self._prefix_size` | ✓ 正确 |
| `import ` | 2,292 | `import the file of the precision of the default to a string in the` | ✗ 散文 |
| `class ` | 2,149 | `class String the file of the string and of the context the stack i` | ✗ 散文 |

### 4.3 分析

**（1）分界线在 5000 次左右**

出现 9000 次以上的模式，模型能写出语法正确的形式；出现 2000 次左右的，退化成自然语言。

这不是巧合：模型对每个上下文的预测能力取决于见过多少次该上下文。样本足够时，它能归纳出「`class` 后面必须跟标识符 + 冒号」这条规则；样本不足时，只能退回到「`class` 是个词，后面接点英文」——而英文散文是语料中最常见的文字形态（注释、docstring）。

**（2）`self.` 的成功也印证了这一点**

`self.` 出现 20,487 次，是语料中最高频的模式（高于 `if` 的 16,937 次）。模型生成的 `self._set_path`、`self._prefix_size` 都是真实的下划线属性命名，形态完全正确。

> **统计口径提醒**：用 `grep -o "self."` 会得到 29,194 这个偏大的数字，因为 `.` 在正则中匹配任意字符，把 `self_`、`selfs` 等也算进去了。模式频率必须用精确字符串匹配（`str.count`），否则会高估 42%。这个细节在评估「低频模式学不会」时很关键——口径错了，阈值判断就会跟着错。

**（3）高温暴露了「只知形状、不知规则」**

```
T=0.3:  def __init__(self, args):
T=0.7:  def __name__(self, and items, name=None):    ← and 是 Python 关键字
```

模型知道「参数位置该放一个词」，但不知道 `and` 不能做参数名。**这是纯统计学习的边界。**

### 4.4 一个可验证的预测

如果语料扩到 3 倍左右（约 2,000 万字符），`class` 的出现次数会涨到 5,000 次以上，跨过 5,000 的分界线。

**预测：届时 `class` 应能生成 `class Foo:` 这样的正确格式。**

**这个预测后来被推翻了**：频率确实跨过了阈值（2,149 → 5,285 次），但格式正确率反而从 17% 降到 0%。
原因分析与新结论见 §5.5——旧语料下那 17% 来自记忆而非泛化。

## 5 实验四：语料规模的影响

§2 的结论是「50 万参数是当前语料下的最优点」。但如果瓶颈在数据呢？
本节把语料从 630 万字符扩到 2,097 万（3.3 倍），模型结构、参数量、训练步数全部不变。

### 5.1 语料从哪来

原语料只用了 Python 标准库的前 6 MB（`prepare_data.py` 的 `MAX_TOTAL_BYTES`）。
标准库总共只有 10 MB，参数调到顶也扩不上去。

新增来源是本项目的虚拟环境：

| 来源 | 可用代码 |
|---|---|
| Python 标准库 | 10.0 MB / 513 文件 |
| site-packages | 127.3 MB / 6,499 文件 |

site-packages 里是 torch、numpy、pandas、scipy、sklearn 的真实源码，
风格比标准库更现代，也更接近「想生成的代码」的样子。

直接拼起来会带入四类污染，脚本用四道过滤处理：

| 过滤 | 排除什么 | 效果 |
|---|---|---|
| 目录黑名单 | test/、torch/_inductor（嵌 C++ 模板）、pygments/lexers（正则字典） | 约 17 MB |
| 生成标记 | 含 auto-generated / do not edit 的文件 | — |
| 内容去重 | 多个包 vendor 的同一份 compat.py | — |
| 单包限流 | 单包最多占 15%，防止一家独占 | torch 42 MB → 3.15 MB |

### 5.2 一个被忽略的坑：非 ASCII 字符挤占词表

第一次生成后覆盖率只有 99.7887%，被丢掉的是 `^` 和 `&` —— 两个真正的运算符。

原因：语料里有 4,682 种不同字符，大部分是 docstring 里的 emoji 和装饰符号
（组合 emoji 会拆出零宽连接符 U+200D）。词表只有 96 个位置，这些字符单个频率不高
但种类极多，把运算符挤了出去。

解法是只保留纯 ASCII 行：

```
丢弃 1.2% 的字符
字符种类   4,682 → 96
覆盖率     99.7887% → 99.9997%（只剩 \t 被丢）
```

代价极小，收益是零 OOV。这一步不做，模型永远写不出 `a & b`。

### 5.3 公平评测：换语料后 val_loss 不可比

这是本节最容易做错的地方。

模型 A 在旧语料的后 10% 上算验证损失，模型 B 在新语料的后 10% 上算。
两个验证集不同，1.7124 和 1.4446 这种数字放在一起比是错的。

正确做法是找一个两版语料都没收录的第三方测试集。
标准库的 `Lib/test` 正好满足：两个数据准备脚本的目录黑名单里都有 `test`。

```
测试集    标准库 Lib/test 的 40 个文件，共 1,624,496 字符
覆盖率    两个模型都是 100.000%（不存在「少算字符」的偏袒）
```

### 5.4 结果

| 模型 | 参数量 | 语料 | loss | ppl |
|---|---|---|---|---|
| A | 495,440 | 630 万 | 1.6608 | 5.264 |
| B | 495,440 | 2,097 万 | **1.4952** | **4.460** |

**ppl 降低 15.3%，loss 降低 10.0%。**

训练过程也更健康：B 跑 30,000 步后 train 1.4331 / val 1.4446，差距只有 0.012，
没有任何过拟合迹象。而语料只有 630 万时，94 万参数的模型在 9,000 步就开始回升。

生成质量量化对比（每模型 60 个样本，temperature=0.6）：

| 模型 | 签名合法 | 参数不重复 | 有函数体 | 引号成对 |
|---|---|---|---|---|
| 10 万 · 旧语料 | 11.7% | 11.7% | 90.0% | 95.0% |
| 50 万 · 旧语料 | 31.7% | 20.0% | 96.7% | 38.3% |
| 50 万 · 新语料 | 31.7% | **26.7%** | **100%** | **66.7%** |

两个指标值得注意：

- **签名合法率没变（31.7%）** —— 它由参数量决定，不由语料决定
- **参数不重复 20% → 26.7%，引号成对 38.3% → 66.7%** —— 这些由语料决定

**参数决定「能不能写出签名」，语料决定「签名写得好不好」。**

另外，新模型的注意力层分工与 §3 完全一致：层 1 熵均值 0.59、层 2 为 1.90
（旧模型是 0.61 / 1.95），图上仍是一条锐利对角线对比一片散点。
图见 `results/attention_big_heads.png` 与 `results/attention_big_layer_avg.png`。

**这个模式换了 3.3 倍语料依然复现，说明「浅层看局部、深层看全局」不是数据巧合，
而是这种架构在语言建模任务上的固有倾向。**

### 5.5 一个被推翻的预测

§4.4 曾预测：语料扩到 2,000 万后，`class` 的出现次数会跨过 5,000 阈值，
届时应能写出 `class Foo:` 的正确格式。

频率确实跨过了：2,149 → 5,285 次。但生成结果是：

| 模型 | `class ` 格式正确率（30 样本） | 典型输出 |
|---|---|---|
| 旧语料 | 17% | `class Entry:`、`class AttributeError(` |
| 新语料 | **0%** | `class is not None:`、`class the same of token` |

**预测被推翻，而且不是小幅偏差，是方向相反。**

进一步检查发现两件事：

**第一，旧模型那 17% 不是泛化，是记忆。**

它吐出的每个类名都来自语料：`AttributeError`（257 次）、`Entry`（21 次）、
`StatisticsError`（53 次）。`Entry` 在全语料里只出现 21 次它都能复现，
这不是学会了「class 后接驼峰标识符」这条规则，而是背下了具体名字。

**第二，新模型的失败才是真实水平。**

它吐的 `the same of`、`when be the` 在两版语料里都是 0 次，是模型自己编的英文。
说明它只学到「`class` 后面接一个词」，没学到「必须是一个合法类名」。

所以准确的结论是：**扩语料没有让模型变差，而是揭穿了它原本就没学会这条规则。**
旧语料规模小、内容单一，模型靠记忆蒙对了一部分，看起来像会了。

这也修正了 §4.4 的归因。原来认为瓶颈是「频率不够」，实际情况是：

- 频率确实是一个因素（`def` 9,387 次能学会，`class` 2,149 次学不会）
- 但**频率够了也不保证学会** —— 如果这条规则超出了模型容量
- 50 万参数、2 层的模型，可能根本没能力抽象出「标识符」这个概念

### 5.6 在大语料上重跑参数扫描

§2 的结论（50 万最优）建立在 630 万字符上。语料翻了 3.3 倍，这个结论需要重测。

方法与 §2 完全一致：同 seed、同 batch、同 30,000 步、eval_batches=100，只改模型尺寸。

| 配置 | 参数量 | 最优 val | ppl | 最优步 | 用时 |
|---|---|---|---|---|---|
| 50 万（d128 h8 ff680 L2） | 495,440 | 1.4293 | 4.18 | 30000 | 194s |
| 94 万（d128 h8 ff640 L4） | 937,216 | **1.3358** | **3.80** | 28000 | 325s |

**94 万比 50 万好 6.54%，远超 3% 的判定线。**

与旧语料对比，两档的性价比完全反转：

| 语料 | 50 万 | 94 万 | 差距 | 94 万是否过拟合 |
|---|---|---|---|---|
| 630 万 | 1.7270 | 1.7048 | 1.3% | **是**（9,000 步见顶） |
| 2,097 万 | 1.4293 | 1.3358 | **6.54%** | 否（28,000 步见顶） |

**§2 的「50 万最优」在新语料下不再成立。**

原因是那时数据只够支撑 50 万参数（数据/参数比 1:13），94 万超出承载能力，
只能开始背训练集。语料翻 3.3 倍后，94 万的数据/参数比变成 1:22，接近经验值
1:20，于是开始正常发挥。

这也说明 §2 那条结论的准确表述应该是：**「在 630 万字符下，50 万是最优点」**——
最优点不是模型的性质，是模型与数据量的联合性质。

代价仍在深度：94 万的耗时是 50 万的 1.68 倍（325s vs 194s）。宽度增加是并行、
几乎免费，层数增加是串行——这个规律再次得到验证。

### 5.7 结论

1. **扩语料对整体指标有效**：ppl −15.3%，且不再过拟合。
2. **扩语料对局部模式不是万能的**：`class` 格式反而退化，因为原来的「好成绩」是记忆。
3. **ppl 和生成质量不是同一条线**：ppl 是全体字符的平均，被高频模式主导；
   低频模式的表现可以完全独立于 ppl 变化。
4. **评测必须用独立测试集**：换语料后拿各自的 val_loss 对比，会得出相反结论。
5. **最优参数量随数据量移动**：630 万字符时 50 万最优，2,097 万字符时 94 万更好（−6.54%）。
   「多少参数最好」不是模型的固有属性，是模型与数据量的联合结果。

## 6 实验五：n-gram 基线

### 6.1 为什么需要它

前五节所有结论都压在一个数字上：ppl 4.460。但这个数字本身没有刻度——它可能意味着「模型很强」，
也可能意味着「字符级任务本来就该这么低」。

唯一的判断办法，是让一个完全不同、而且明显更笨的模型做同一道题。

n-gram 就是那个笨模型。它的全部能力一句话说完：**数一数历史上「片段 A 后面跟着字符 c」
出现过多少次**，再按比例押注。没有注意力、没有梯度、没有反向传播，连「学习」都谈不上——只是在数数。

它在 2000 年代是统计机器翻译和语音识别的主力，也是语言建模的经典强基线。
一个 50 万参数的 Transformer 如果打不过它，那一堆矩阵乘法就白算了。

### 6.2 它怎么算

    5 阶（用前 4 个字符预测下一个）的插值绝对折扣公式：

    p(c | h) = max( count(h,c) − D, 0 ) / count(h)          ← 见过的，打个折
             + D · U(h) / count(h) · p(c | h′)              ← 剩下的分给短上下文

- `h` 是前 n−1 个字符（上文），`U(h)` 是 h 后面出现过多少种不同字符
- **减 D**（绝对折扣，D=0.9）：见过一次不代表下次一定见，抠掉一点概率分给没见过的字符
- 抠出来的概率按 `U(h)` 摊给「退一步的短上下文」`h′`，一路退到只看单个字符
- 这是 Kneser-Ney 平滑的简化版（不做 continuation count）

一个 n-gram 模型的「参数」就是那张计数表，每个「上文 → 字符」的格子存一个数。
本次实测：4 阶表 501,300 格，5 阶表 1,143,081 格，累计 **1,777,634 格**。

### 6.3 怎么保证公平

五条，缺一条结论就不成立：

1. **同一份训练语料**：`data/corpus_big.txt`
2. **同一个测试集**：直接复用 `experiments/eval_cross.py` 的 `build_test_text()`——同一批文件、同一随机种子、同一段文本
3. **同一个字符流**：只保留词表内 96 个字符，映射成和 Transformer 完全一样的 id 序列
4. **同样的上下文长度**：上下文每 64 字符清零一次，对齐 `seq_len`。另给一组「不清零」的结果作为上限
5. **参数不偷看测试集**：折扣系数 D 在验证集上剪（语料后 10%，和 Transformer 的 val 同一段）

D 的裁剪结果（2,097 万语料，验证集）：

| 阶数 | D=0.25 | D=0.50 | D=0.75 | D=0.90 |
|---|---|---|---|---|
| 2-gram | 13.036 | 13.035 | 13.035 | 13.035 |
| 3-gram | 7.558 | 7.534 | 7.526 | 7.529 |
| 4-gram | 5.522 | 5.412 | 5.367 | 5.362 |
| 5-gram | 5.020 | 4.793 | 4.693 | **4.676** |

低阶几乎不受 D 影响（2-gram 四列只差 0.001），高阶敏感（5-gram 差 6.8%）。
两个语料上都选出 D=0.90、5 阶，所以最终统一用这个设置。

### 6.4 结果

测试集：标准库 `Lib/test` 的 40 个文件前 400,000 字符（与 §5.3 完全同一段）。

| 阶数 | 计数表条目 | loss | ppl | 该阶上文在训练集里没见过 |
|---|---|---|---|---|
| 1-gram | 97 | 3.3030 | 27.195 | 0% |
| 2-gram | 8,276 | 2.5366 | 12.637 | 0% |
| 3-gram | 124,880 | 2.0483 | 7.755 | 1.6% |
| 4-gram | 501,300 | 1.7988 | 6.042 | 4.0% |
| 5-gram | 1,143,081 | 1.7283 | 5.631 | 9.4% |
| 5-gram（上下文不清零） | 1,143,081 | 1.7103 | 5.530 | 4.9% |
| **Transformer** | **495,440 参数** | **1.4952** | **4.460** | — |

两处口径说明：n-gram 实际计入 393,750 个字符（跳过每段第一个字符，它没有上文可看，
Transformer 在同样的位置也不做预测）；「上下文不清零」一行的未见率反而更低，
是因为清零会制造大量「含起点标记」的罕见上文。

三个读法：

**（1）参数量对齐时，Transformer 好 26%。**

4-gram 的计数表 501,300 格，和 Transformer 的 495,440 个参数几乎一模一样（差 1.2%）。
同样多的「存数字的格子」，ppl 6.042 vs 4.460——**低 26.2%，loss 低 16.9%**。

**（2）把 n-gram 的表扩到 3.6 倍，仍然差 21%。**

5-gram 表 1,143,081 格，累计 1,777,634 格（Transformer 的 3.6 倍），ppl 5.631，
**仍比 Transformer 差 20.8%**。

严格说计数和权重不是一回事（计数是频率，权重是可微的参数），但两者都是「存一个数」，
这个对比至少能回答「是不是只要内存够就能追上」。

**（3）上下文长度不是它落后的原因。**

5-gram 不清零上下文（相当于给它无限长的记忆，Transformer 只有 64 字符），
ppl 也只从 5.631 降到 5.530，仍显著高于 4.460。
**它缺的不是上下文，是把上下文用起来的方式。**

### 6.5 数据的作用对两者不一样

同一套流程在旧语料（630 万字符）上的结果：

| 模型 | 计数表 / 参数量 | loss | ppl |
|---|---|---|---|
| 4-gram | 219,735 | 2.0606 | 7.851 |
| 5-gram | 460,732 | 2.1099 | **8.247** |
| Transformer | 495,440 | 1.6608 | 5.264 |

**旧语料上 5 阶反而比 4 阶差**（8.247 vs 7.851）——15.2% 的 5 阶上文在训练集里根本没出现过，
阶数越高越容易撞空，撞空就只能退回去猜。

语料扩到 3.3 倍后：

| | 旧语料 | 新语料 | 变化 |
|---|---|---|---|
| 5-gram | 8.247 | 5.631 | **−31.7%** |
| Transformer | 5.264 | 4.460 | **−15.3%** |

n-gram 对数据更敏感，因为它的每一点本事都是「记住一段字符」，数据多就等于能背的更多；
Transformer 反而没那么敏感，因为它本来就在压缩规律而不是存原文。

但**收益更高不等于能追上**：n-gram 多降的 16 个百分点，全被它原本更大的差距吃掉了。

### 6.6 为什么加阶数会失效

| | 条目数 | 只出现过 1 次 | 平均次数 |
|---|---|---|---|
| 4-gram | 501,300 | 36.6% | 41.84 |
| 5-gram | 1,143,081 | **43.7%** | 18.35 |

到 5 阶，将近一半的格子只见过一次。再加到 6 阶只会更稀。

更关键的是**每一条上文彼此独立**：`def _ini` 和 `def xyz` 在计数表里毫无关系，
后者不会因为前者学过而受益——这正是「数据稀疏」在 n-gram 里无解的原因。

Transformer 的 495,440 个参数被所有上下文共享：`def _ini` 上学到的东西会自动用在 `def xyz` 上。
**这就是它用更少的格子做到更低 ppl 的全部秘密。**

### 6.7 生成上的差别

同样的开头、同样的温度（0.8）、同样 110 个字符。Transformer 关掉 top-k 截断（`--top-k 96`），
两边都是纯温度采样：

n-gram（5 阶）：

```
def __inition,
         "gradients an edge of ther.__init__(self._check_sample for than zero
```

Transformer：

```
def _lines(self):
        return metric(self, convert, count_hist, orterer, igher):
```

n-gram 的**局部像得惊人**：`__init__`、`self._check`、`"gradients` 全是语料里的原片段，
逐字符看几乎挑不出错。但它没有「一个函数该长什么样」的概念，
几个字符之后就开始把不同文件的片段缝在一起，逗号直接出现在函数名后面。

Transformer 的情况正好相反：参数名是编的（`orterer`、`count_hist`），
但括号、冒号、缩进、`return` 的骨架是对的。

**这解释了 §4 的那个现象**：ppl 是每字符平均，谁在局部更像谁就占便宜；
而「代码是不是代码」取决于骨架，那需要跨越几十个字符的结构信息。

### 6.8 结论

1. **Transformer 赢了，但优势不是压倒性的**：容量对齐时 ppl 低 26%，容量 3.6 倍时低 21%。
2. **差距来自参数共享，不来自上下文长度**：给 n-gram 无限上下文也只从 5.631 到 5.530。
3. **n-gram 是最便宜的可信下限**：数一遍语料 2.5 秒、不用 GPU、只用 numpy，
   就能给出 5.631 这个参照——任何语言模型项目都该先跑它。
4. **ppl 4.460 现在有刻度了**：它比「只数数的模型」好 21–26%，但离「懂代码」还很远——
   这与 §5.5 的 `class` 生成失败是同一件事的两个侧面。

## 7 局限

诚实列出这次工作没做到的部分：

**（1）分词粒度过粗**

字符级词表只有 96 个 token。模型要花大量参数去记「`d` 后面常跟 `e`」这种低级规律。同样参数量下，BPE 分词（把 `def`、`self.`、`return` 当成单个 token）能表达多得多的语义，序列长度还会缩短 2-3 倍。

**（2）语料仍然单一**

已从 630 万扩到 2,097 万（§5），但全部是 Python 源码，没有自然语言、没有其他编程语言。
模型学到的是「Python 的字符统计规律」，不是通用语言能力。

**（3）深度不足**

只有 2 层。论文用 6 层，更深的模型能组合出更复杂的模式。但本次实验显示加深的代价远高于加宽（+73% 时间），在 8 GB 显存的笔记本上需要权衡。

**（4）基线只覆盖了最低的一档**

§6 补上了字符级 n-gram，但它只是「不学」的那一端。中间档缺失：LSTM 语言模型、
BPE 词表下的 n-gram、以及同样参数量但训练更久的 Transformer。
只有两端（纯计数 vs 495,440 参数）无法回答「多大的模型才够用」这个问题。

**（5）基线对 n-gram 是有利设置，仍应警惕**

n-gram 数数时用的是**整条连续语料**，而 Transformer 训练时只看到 64 字符的窗口——
上下文信息上 n-gram 占了便宜，结果它仍然输了 21%。方向没问题，但严格来说这不是
同等条件下的对决。

**（6）量化指标仍然较粗**

已补 `experiments/eval_generation.py`（签名合法率等四项）与
`experiments/check_class_threshold.py`（专项模式检验），但指标只看首行格式与参数列表，
不检查函数体语义。更严格的做法是用 `ast.parse` 统计整体可解析率。

§6.7 的生成对比是单样本的定性观察，没有做统计。要让「骨架 vs 碎片」这个说法站得住，
应该对 100 个样本统计括号平衡率、缩进一致性、`ast.parse` 通过率。

按优先级排序：

**（1）把主模型切到 94 万**（已完成扫描，见 §5.6）

在新语料上 94 万比 50 万好 6.54%，且未过拟合。切换需要重训一次（约 5.4 分钟），
并同步更新 `src/config.py`、生成样例、注意力图与 webapp 的默认检查点。

**（2）补中间档基线**

在 §6 的两端之间插一个 LSTM（同 50 万参数）和一个 4 层 Transformer。

**（3）换 BPE 分词**

在扩语料之后再做，否则只会加速过拟合。
